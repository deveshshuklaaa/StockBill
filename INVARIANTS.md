# StockBill business invariants

- Inventory balances are stored per product and warehouse in base units. `Product.current_stock` remains a compatibility cache equal to the sum of balances in **sellable** warehouses (`Warehouse.is_sellable`). Non-sellable warehouses (only `DAMAGED`, "Damaged / Quarantine", created by migration `inventory/0018`) keep full balances and ledger rows but are left out of that cache and of the dashboard stock figures; the inventory report keeps them in its totals and splits them out as `held_*`. With no non-sellable stock the cache equals the all-warehouse sum, as before.
- An invoice's stock source is `Invoice.source_warehouse`; null means `MAIN` (every invoice before the field existed). It is fixed at posting, cancellation returns stock to it, an amendment's replacement inherits it, and it can never be a non-sellable or inactive warehouse.
- A credit note's stock destination is `CreditNote.destination_warehouse`; null means `MAIN` (every earlier credit note). Damaged returns go to `DAMAGED`: held for 1:1 supplier replacement, never written off.
- Damaged goods leave for the supplier as an append-only `SupplierReturn` (`PURCHASE_RETURN` movement, default out of `DAMAGED`) and come back as `SupplierReplacementReceipt`s (`PURCHASE` movement, reference type `supplier_replacement`, default into `MAIN`) capped at the returned quantity. Neither leg changes WAC. Both tables are append-only in the model and through the `stockbill_protect_supplier_ledger()` trigger.
- Every balance-changing operation runs inside `transaction.atomic()`, locks the relevant balance with `select_for_update()`, and creates a `StockLedger` event.
- Product conversion factors must be positive. Invoice lines now capture entered unit (piece/master box), conversion factor, and base quantity; stock deduction uses base quantity.
- Sale lines snapshot `cost_price_snapshot` and `cogs_amount`; changing a product's current cost does not change historical gross profit.
- Posted invoices are read-only through the API. Corrections use credit notes; products are archived rather than deleted.
- Draft invoices are created through `/api/invoices/drafts/` and post through `/api/invoices/{id}/post/`; posting is the point at which inventory and cash-ledger effects occur.
- Posted invoice lines and payments are immutable at both API and model boundaries. Invoice cancellation uses `/api/invoices/{id}/cancel/`; payment correction uses `/api/payments/{id}/reverse/`.
- PostgreSQL triggers additionally block bulk ORM updates/deletes for posted invoices/lines, payments, reversals, credit notes, audit logs, stock ledger rows, and direct inventory-balance changes. Inventory services set a transaction-local authorization flag only while updating balances.
- Invoice and line snapshots are used for historical detail/PDF output; current product/customer records are not required to reconstruct posted documents.
- Payment creation is actor-aware: the API passes the authenticated user to the payment service and records that user in `AuditLog`. Staff may receive/create payments and create validated credit notes; only admins may cancel invoices or reverse payments. DebitNote is a model foundation only and has no active write API.
- PDF verification is split: `render_invoice_html()` is tested against immutable snapshots; binary WeasyPrint generation remains an environment-specific integration step when native libraries are available.
- Payments are append-only through the API. A correction requires a future reversal/adjustment transaction.
- Credit notes cannot exceed the original line quantity minus prior reversals and return stock transactionally.
- Invoice creation accepts an `Idempotency-Key`; retries return the original invoice.
- Customer outstanding balance is opening balance plus invoices minus payments minus credit notes.
- Supplier balance (`inventory/supplier_ledger.py`) = Σ POSTED purchase totals + Σ replacement receipts + Σ payment reversals − Σ supplier payments − Σ supplier returns. **Positive = Payable** (we owe the supplier), **negative = Advance** (paid ahead). There is no opening-balance field; a date-filtered statement only brings earlier entries forward. Drafts and cancelled purchases never count.
- `SupplierPayment` / `SupplierPaymentReversal` are append-only exactly like `Payment` / `PaymentReversal` (model guards plus `stockbill_protect_supplier_ledger()` trigger; amount > 0 by DB check). Staff create payments; only admins reverse them, partially or fully, never beyond the paid amount.
- GST (`billing/tax_engine.py`): each line snapshots the product's configured rate and HSN/SAC code. Place of supply defaults to the customer's state code (else the seller's) and can be set per invoice; intra-state supply splits tax into CGST/SGST (CGST rounded to paise, SGST = line tax − CGST), inter-state supply goes wholly to IGST. Tax-exclusive and tax-inclusive pricing are both supported. Not implemented: e-invoicing/IRN, e-way bills, reverse charge, and credit-note PDFs; StockBill output must not be represented as covering those.
- Tax-invoice numbers (CGST Rule 46(b)) are assigned only by the server, only at the transition into POSTED (`post_invoice`, the direct-post path of `create_invoice`, and the amendment replacement), from a per-financial-year series `<INVOICE_NUMBER_PREFIX>/<yy-yy>/<5-digit serial>`, e.g. `DE/26-27/00001`. Drafts have `invoice_number = NULL` (DB check constraint: only DRAFT rows may be unnumbered). Any client-supplied `invoice_number` is ignored.
- Numbers are reserved inside the posting transaction under a PostgreSQL advisory lock (`billing/numbering.py`, same pattern as purchase numbering), after all stock and credit-limit validation; a failed or rolled-back post consumes no serial, so the series is consecutive and gapless. The financial year comes from `timezone.localdate()` (IST), never UTC. Every issued number must match `^[A-Za-z0-9/-]{1,16}$`; a prefix that would break this raises instead of issuing.
- `invoice_date` is the IST posting (issue) date, set when the number is assigned; before posting it is only the draft-creation date. On POSTED/CANCELLED invoices both `invoice_number` and `invoice_date` are immutable (model guard and `stockbill_protect_history` trigger).
- Legacy invoices numbered `INV-YYYYMMDDHHMMSS` (browser-generated before server numbering) are a closed series and are never renumbered. The new series for FY 26-27 started at serial 1 unless moved with `python manage.py set_document_counter --doc invoice --fy 26-27 --last-serial N`, which refuses to go below an issued serial and writes an AuditLog row.
- Credit notes (CGST Rule 53) carry `credit_note_number` `<CREDIT_NOTE_NUMBER_PREFIX>/<yy-yy>/<serial>`, e.g. `CN/26-27/00001`, assigned in the same transaction that creates the note. Credit notes that existed before numbering were backfilled in `(created_at, id)` order by FY of `note_date` (migration `billing/0018`, which briefly disables only the `billing_creditnote` append-only trigger), and the counter continues from there.
- Invoice lists, reports and summaries order by `(invoice_date, id)`, never by the number string, because legacy and new numbers do not sort together.
- Tax migration note: legacy product slabs are mapped to seeded TaxRate rows; legacy invoice tax is split CGST/SGST as an explicit approximation because historical place-of-supply data was unavailable.
- Historical migrated products are seeded into `Main Warehouse` with an `OPENING_STOCK` ledger event.
